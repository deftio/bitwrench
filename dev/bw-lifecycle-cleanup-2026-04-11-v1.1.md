## What is bitwrench?

Bitwrench is a lightweight JavaScript UI library (~38KB gzipped, zero
dependencies) that takes a different approach from React, Vue, and Angular.
Instead of templates, compilers, and virtual DOMs, bitwrench uses plain
JavaScript objects called TACOs to define UI components.

A TACO (Tag, Attributes, Content, Options) is a component specification:

```javascript
{
  t: 'div',                          // tag
  a: { class: 'stats-card' },        // attributes
  c: [                                // content (children)
    { t: 'h3', c: 'Revenue' },
    { t: 'span', a: { class: 'value' }, c: '$0' }
  ],
  o: {                                // options (lifecycle + behavior)
    state: { value: 0 },
    slots: { value: '.value' },
    handle: {
      setValue: function(el, v) {
        el._bw_state.value = v;
        el.bw.setValue('$' + v);
      }
    }
  }
}
```

This is not a template or a render instruction. It's a component
definition -- like a CButton in MFC, a JTextField in Swing, or a TEdit
in Delphi. The TACO declares structure, state, and behavior. bitwrench
turns it into a live DOM element with a public API (`el.bw.setValue(42)`)
that the component uses to manage its own rendering.

### Why not React/Vue/Angular?

Those frameworks start from a premise: the DOM can't be trusted, so build
a virtual representation, diff it, and patch the real DOM. This works, but
it requires compilers (JSX, SFC, template syntax), runtimes (reconcilers,
reactive proxies, change detectors), and toolchains (Babel, Webpack/Vite,
HMR). The template is not the component -- the compiled output is.

Bitwrench starts from the opposite premise: **the DOM IS the component.**
A TACO becomes a real DOM element. That element has methods (`el.bw.*`),
state (`_bw_state`), and lifecycle hooks. You call methods on it, it
updates itself. No virtual intermediary, no diffing, no compiler.

This is how desktop UI frameworks have always worked. MFC: you call
`SetWindowText()`, the control repaints. Swing: you call `setText()`,
the component repaints. You don't diff a virtual window tree.

### Key architectural properties

**TACO is data.** A TACO is a plain JS object. It can be serialized to
JSON (minus functions in `o`), sent over the wire, stored in a database,
validated against a JSON Schema, generated by an LLM, or created by a
server in any language. No compiler output, no opaque descriptors.

**DOM IS the registry.** Every bitwrench component is findable via
standard CSS selectors (`querySelector('.bw_is_component')`). No framework
extension, no React DevTools, no special tooling needed. Browser DevTools,
Playwright, and LLMs can find and interact with bitwrench components using
the DOM API that already exists.

**Components own their rendering.** Users call `el.bw.setTitle('New')`,
not `el.querySelector('.title').textContent = 'New'`. The component
decides how to update its DOM. This is the MFC/Swing model: the component
is the API, the DOM is the implementation detail.

**No build step required.** TACO works interpreted (zero toolchain) and
compiled (production optimization). Reactivity comes from the component
model, not from a compile step. A component's `el.bw.method()` triggers
updates because the component was built that way, not because a compiler
wired signal subscriptions.

**CSS generated from JS.** Because TACO is JS, CSS is also JS. `bw.css()`
generates CSS from palette objects. `bw.makeStyles()` generates an entire
design system from seed colors. No Less, Sass, Tailwind, or CSS custom
properties needed. Theme switching via `bw.toggleThemeMode()` swaps the
palette object and regenerates.

**Server-driven UI.** bwserve pushes TACOs from server to client via SSE.
The server controls the UI. Closest analogue: Phoenix LiveView, not any
JS framework. Because TACOs are data, any backend language can generate them.

**LLM-native.** LLMs generate JSON naturally. A TACO is JSON. An LLM can
generate a bitwrench UI, validate it against a schema, and the client
renders it without any compilation. bwattach lets an LLM directly drive
a running bitwrench page: inspect components, call methods, screenshot.

### Target use cases (near-term focus)

- Embedded systems UI (ESP32 serves static HTML, updates via JSON/SSE)
- LLM-generated UI (schema-validated TACO generation, fraction of the
  tokens/compute vs JSX frameworks)
- Server-driven dashboards (bwserve pushes TACOs, client renders)
- Rapid prototyping (zero toolchain, script-tag deployment)
- Internal tools and admin panels (Bootstrap-tier effort, component-tier result)
- Teams that want component architecture without framework lock-in

The near-term focus is embedded devs and LLM devs -- use cases where
bitwrench's compactness, zero-toolchain deployment, and data-as-UI model
are immediate advantages. The architecture doesn't have a ceiling: no
compiler to maintain, no VDOM to diff, schema-enforced UI patterns, server-
side rendering, remote debug, and a fraction of the compute. Where it
goes from here depends on how well we execute the fundamentals.

This document specifies the v2.1.0 lifecycle cleanup: how bitwrench

**Design principles for this release**:

- Breaking changes are acceptable -- 2.1.0 is the right place for them

- TDD: write spec tests for new behavior first, then implement

### Scope: everything that touches the lifecycle

This release cleans up the entire pipeline: bitwrench core, bwserve
protocol, and bwcli. All three must be internally consistent. A function
name in core must match the protocol message type in bwserve and the
CLI subcommand in bwcli. If existing functions are wired wrong, rewire
them. If existing protocol message types don't map cleanly, rename them.
v2.1.0 is the foundation release -- what ships here is what experienced
developers will judge.

### bwcli: zero-dependency server-side tool

bwcli is four things:
1. **Dev server** -- serve bitwrench pages with live reload
2. **Streamlit-ish replacement** -- Python/Node backend pushes TACOs to
   browser via bwserve, no frontend code needed
3. **Server-side debug tool** -- bwattach connects to running pages,
   inspect components, call methods, screenshot
4. **Ambassador for bitwrench** -- first thing a new developer runs.
   Must be polished, fast, and impressive.

**Zero external dependencies.** bwcli is server-side only. It runs on
modern Node.js (v20+) or Bun. Use built-in APIs exclusively:

| Need | Use | NOT |
|---|---|---|
| HTTP server | `node:http` / `node:https` | express, koa, fastify |
| File system | `node:fs/promises` | fs-extra, glob |
| Path handling | `node:path` | path-extra |
| HTTP requests | `node:fetch` (global) | axios, node-fetch, got |
| File watching | `node:fs.watch` | chokidar |
| Child processes | `node:child_process` | execa |
| Crypto/hashing | `node:crypto` | uuid, nanoid |
| URL parsing | `node:url`, `URL` global | url-parse |
| Streams | `node:stream` | through2, pump |
| Testing | `node:test` + `node:assert` (for bwcli's own tests) | jest, vitest |
| CLI arg parsing | Manual (bwcli has <20 commands) | yargs, commander |
| WebSocket | `ws` (only if WebSocket transport added -- defer) | socket.io |
| Compression | `node:zlib` | compression |

The only acceptable exception is `ws` for WebSocket transport (no Node
built-in yet). Everything else uses Node/Bun built-ins. If a built-in
API is clunky, write a 10-line wrapper -- don't add a dependency.

Developers must run Node 20+ or Bun. This is stated in the README.
No polyfills, no fallbacks for Node 14/16.

## The Lifecycle Phases

Every bitwrench UI element follows this state machine:

```
define --> create --> hydrate --> mount --> update --> unmount
  |                                          ^         |
  |          (string path)                   |         |
  +------> bw.html() -----> HTML string      +---------+
```

In practice, **create and hydrate are fused inside createDOM** because
createDOM has both the TACO and the node in hand at each recursive step.
Standalone `bw.hydrate()` exists as a public API for a different use case:
wiring lifecycle onto externally-created DOM (server-rendered HTML, third-
party elements). The normal pipeline is:

```
bw.DOM('#app', taco)   = cleanup + createDOM(create+hydrate) + mount
bw.mount('#app', taco) = cleanup + createDOM(create+hydrate) + mount, returns root
```

The 6-phase model is useful for understanding WHAT happens at each step.
The implementation fuses create+hydrate for practical reasons.

## Phase 1: Define

User writes a TACO object. Pure data, no side effects.

| | |
|---|---|
| **Function** | None. User writes `{t, a, c, o}` manually, uses `bw.h()`, or calls a `bw.make*()` factory. |
| **Input** | User's intent |
| **Output** | TACO object `{t, a, c, o}` |
| **Side effects** | None |
| **Identity** | None. User MAY pre-assign via `bw.assignUUID(taco)`. |
| **In document** | No |

**The TACO is consumed, not stored.** After creation and hydration, the
TACO has done its job. bitwrench does not retain a reference to it. All
information from `o` is decomposed onto the DOM element's properties during
hydrate. If you need another instance, call the factory again or clone the
TACO at define time. "Clone TACOs, not DOM nodes."

If a future use case requires storing the TACO on the element, store a
proper deep clone (structure + shared function refs), not a partial extract.
A real TACO is easy to inspect and debug; a half-baked subset is not.

### o.* Options (complete set for v2.1.0)

| Option | Type | Purpose | Stored as | Cleaned by |
|---|---|---|---|---|
| `o.state` | Object | Component's local mutable state | `el._bw_state` | cleanup (deleted) |
| `o.render` | Function(el, state) | Full subtree rebuilder. Called by `bw.refresh()`. **Heavy path.** | `el._bw_render` | cleanup (deleted) |
| `o.mounted` | Function(el, state) | Post-mount hook. Called once, synchronously, when element enters document. | `el._bw_mounted_fn` (temporary) | mount (deleted after call) |
| `o.unmount` | Function(el, state) | Pre-cleanup hook. Called during `bw.cleanup()`. | `_unmountCallbacks.set(uuid, fn)` | cleanup (called then deleted) |
| `o.handle` | Object `{name: fn(el, ...args)}` | Public methods bound to `el.bw`. PRIMARY update mechanism. | `el.bw[name]` | cleanup (deleted) |
| `o.slots` | Object `{name: selector}` | Declarative DOM targets. Auto-generates `el.bw.setName()`/`getName()`. Cached querySelector at hydrate time. | getter/setter pairs on `el.bw` | cleanup (deleted) |
| `o.type` | String | Component type tag for typed discovery. | `el._bw_type` + `bw_is_component_bccl_{type}` class | cleanup (deleted) |

This set is final for v2.1.0. No additions.

**Auto-render-as-mounted**: If `o.render` is present and `o.mounted` is
absent, hydrate synthesizes a mounted function that calls render. This
means `o: { state: {}, render: fn }` just works -- the component renders
itself when mounted. This is documented behavior, not magic. If you need
custom mount logic, provide `o.mounted` explicitly.

## Phase 2+3: Create + Hydrate (fused in createDOM)

createDOM builds a DOM tree from a TACO and wires lifecycle onto elements
that have `o.*` options. These are conceptually two phases but implemented
in one recursive pass because createDOM has both the TACO and the node at
each step.

| | |
|---|---|
| **Function** | `bw.createDOM(taco)` |
| **Input** | TACO object (or primitive, null, bw.raw()) |
| **Output** | DOM node with lifecycle wired but NOT mounted |
| **Side effects** | Event listeners attached. _bw_state/el.bw/etc stored on elements with `o`. |
| **Identity** | Pre-assigned UUIDs preserved in class string. Elements with `o.*` lifecycle options get auto-assigned UUID in class string (structural identity for _bw_refs keying). NOT registered in _nodeMap until mount. |
| **Classes stamped** | `bw_lc` (lifecycle marker), `bw_is_component`, `bw_is_component_bccl_{type}` -- on elements with `o.*` |
| **In document** | No |

### What createDOM does (create part):

- null/undefined -> empty text node
- bw.raw() -> fragment via innerHTML
- Primitives (string, number) -> text node
- TACO with `.t` -> createElement (or createElementNS for SVG)
  - Set attributes (style, class, events, value, booleans)
  - Build children recursively
  - Build `_bw_refs` map (id/pre-assigned-uuid keyed child references)
  - Register in `_nodeMap` if element has `id` attribute

### What createDOM does (hydrate part, for elements with `o`):

1. Determine if this is a lifecycle element: has `o.state`, `o.handle`,
   `o.mounted`, `o.unmount`, `o.render`, or `o.slots`
2. If yes:
   a. Add `bw_lc` class (lifecycle/cleanup marker)
   b. Add `bw_is_component` class
   c. If `o.type`: add `bw_is_component_bccl_{type}` class,
      store `el._bw_type = o.type`
   d. Store `el._bw_state = o.state` (if present)
   e. Store `el._bw_render = o.render` (if present)
   f. Store `el._bw_mounted_fn` (from o.mounted, or synthesized from
      o.render if o.mounted absent)
   g. Store `el._bw_unmount_fn = o.unmount` (if present)
   h. Create `el.bw = {}` handle namespace
   i. Bind handle methods: `el.bw[key] = o.handle[key].bind(null, el)`
   j. Create slot getters/setters (cached querySelector on built tree)

### What createDOM does NOT do (deferred to mount):

- Register UUID in `_nodeMap` (UUID class IS stamped during create for
  _bw_refs, but not registered in _nodeMap until mount)
- Move `_bw_unmount_fn` to `_unmountCallbacks` registry
- Fire `mounted()` callback

### Standalone bw.hydrate(node, taco)

Public API for wiring lifecycle onto an externally-created DOM node.
NOT part of the normal pipeline (createDOM handles it internally).

Use case: server-rendered HTML, third-party DOM, or manual element creation
where you have a DOM node and a TACO with `o.*` options to wire onto it.

hydrate walks `taco.c` and matches children to `node.childNodes` by tag
and position. For each match where the taco has `o`, it wires lifecycle
(same steps as createDOM's hydrate part). Text nodes and raw fragments
are skipped (no lifecycle to wire).

hydrate is idempotent: if `el.bw` already exists or `bw_lc` class is
present, skip that element (already hydrated).

## Phase 4: Mount

Element is placed in the document. UUID stamped. Registered in caches.
mounted() fires synchronously.

| | |
|---|---|
| **Function** | Internal `_mountTree(node)`, called by bw.DOM() and bw.mount() after appendChild |
| **Input** | Hydrated node that is now in the document |
| **Output** | Same node, now alive and addressable |
| **Side effects** | UUID stamp, _nodeMap registration, _unmountCallbacks registration, mounted() fires |
| **Identity** | `bw_uuid_*` stamped on every `.bw_lc` element in the tree |
| **In document** | YES |

### What mount does:

1. Walk tree for `.bw_lc` elements:
   a. Check for pre-assigned UUID via `bw.getUUID(el)`
   b. If UUID exists AND `_nodeMap[uuid]` points to a different live element:
      **warn and skip** (UUID collision -- soft error, not throw)
   c. If UUID exists and no collision: use it
   d. If no UUID: generate `bw.uuid('uuid')`, add class
   e. Register `_nodeMap[uuid] = el`
   f. If `el._bw_unmount_fn`: move to `_unmountCallbacks.set(uuid, fn)`,
      delete `el._bw_unmount_fn`
   g. If `el._bw_mounted_fn`: call it `(el, el._bw_state || {})` in
      try/catch, delete `el._bw_mounted_fn`

### mounted() fires synchronously

No requestAnimationFrame. The element IS in the document when mounted()
runs. This is a behavioral change from 2.0.x (which used rAF). The
synchronous model is correct: mounted() should be able to measure the
element, start animations, set up IntersectionObservers, etc.

### UUID collision is a soft error

If a pre-assigned UUID collides with an already-mounted element, mount
logs a console warning and skips that element's lifecycle registration.
The element is structurally in the DOM (appendChild already happened) but
has no lifecycle (not in _nodeMap, mounted doesn't fire). This is graceful
degradation. A hard throw would leave the DOM in partial state with some
children registered and others not.

## Phase 5: Update

Mounted component changes state or content. Operations are ordered from
cheapest (component handles it) to most expensive (full rebuild).

### Operation API

| Function | What it does | Cost | Preserves focus? |
|---|---|---|---|
| `el.bw.method(args)` | Component-owned DOM surgery | Cheapest | YES |
| `el.bw.setSlot(value)` | Replace content at cached slot target | Cheap | YES |
| `bw.message(ref, action, data)` | Dispatch to `el.bw[action](data)` | Cheap | YES |
| `bw.update(ref, data)` | Smart dispatch: `el.bw.update(data)` if exists, else `bw.refresh(ref)` | Cheap or expensive | Depends |
| `bw.patch(ref, content)` | Modify in place: attrs (object), text (string), or children (TACO/array) | Cheap-medium | YES |
| `bw.append(ref, content)` | Add child without destroying existing children | Medium | YES |
| `bw.replace(ref, taco)` | Replace the element ITSELF at its DOM position | Expensive | NO |
| `bw.refresh(ref)` | Tear down children, call _bw_render, rebuild | Expensive | NO |
| `bw.remove(ref)` | Cleanup + remove from DOM | One-way | N/A |

### bw.update(ref, data) -- the smart dispatch

```
bw.update(ref, data):
  1. el = bw.el(ref)
  2. if data provided AND el.bw.update exists: el.bw.update(data)
  3. else if el._bw_render exists: bw.refresh(ref)
  4. else: warn "no update method or render function"
```

`bw.update(ref)` with no data = refresh (rebuild from render).
`bw.update(ref, data)` with data = method dispatch to el.bw.update(data).

This means the component author controls what "update" means. A simple
counter component's `update` method increments a number. A dashboard's
`update` method dispatches to 5 slot setters. The caller doesn't need to
know the internals -- just "here's new data."

### bw.refresh(ref) -- the heavy path

Destroys ALL children's focus, scroll position, CSS transitions, input
state, and **child component state**. Use only when DOM structure must
change (view swap, structural reconfiguration).

**Child component state is destroyed by refresh.** This is the #1 thing
React developers will trip over. React preserves child state across parent
re-renders (via key matching). bitwrench refresh rebuilds from scratch --
new child components, new state. If you need to preserve child state,
use handle methods and slots instead of refresh.

### bw.replace(ref, taco) -- swap element (NEW)

Replaces the element ITSELF at its DOM position. Cleanup old element,
create+hydrate+mount replacement at same position in parent. Use case:
swap a loading placeholder for a real component, swap one view for another.

**Returns the new element.** `var chart = bw.replace(display, makeChart({}));`
The old element reference is stale after replace. Callers need the new ref.

If taco is null: equivalent to `bw.remove(ref)`. Returns null.

### bw.append(ref, content) -- add child (NEW)

Creates and mounts new child without destroying existing children. The
common pattern for lists, notification feeds, chat messages. Content goes
through full pipeline: createDOM + _mountTree.

### bw.remove(ref) -- cleanup + remove (NEW)

`bw.cleanup(el); el.remove()`. Currently a manual 2-line pattern. Making
it a first-class function enables bwserve and bwcli to use it cleanly.

### bw.patch(ref, content) -- modify in place

Keeps all current overloads:
- Object: set attributes (`bw.patch(ref, {disabled: true})`)
- String/number: set text content (`bw.patch(ref, 'new text')`)
- TACO/array: replace children (`bw.patch(ref, newTaco)`)

The TACO/array path now calls cleanup on old children before replacement
(GAP-3 fix). New content goes through full create+hydrate+mount pipeline.

### bw.updateSlot(ref, slotName, valueOrApplyFn) -> value[] (NEW)

Broadcast slot update across one or many matched components.
- ref: element, UUID string, or CSS selector
- If valueOrApplyFn is a function: `fn(currentValue) -> newValue`
- Always returns an array (even single match)

### Error handling

bitwrench does not catch exceptions in handle methods or render functions.
Errors propagate to the caller. If `bw.refresh()` fails mid-render
(render function throws), children are in torn-down state with no new
content. This is the developer's responsibility. Wrap render functions
in try/catch if you need error boundaries.

### Async data population

Component mount is always synchronous. Async is for data, not structure:

```javascript
o: {
  state: { rows: [], loading: true },
  mounted: function(el, state) {
    fetch('/api/data').then(function(r) { return r.json(); })
      .then(function(rows) { el.bw.setRows(rows); });
  },
  handle: {
    setRows: function(el, rows) {
      el._bw_state.rows = rows;
      el._bw_state.loading = false;
      // build row TACOs, patch into table body
    }
  }
}
```

Component is fully alive and interactive while data loads. No Suspense,
no framework-level async. The developer renders a loading state, then the
handle method replaces it when data arrives.

### Conditional rendering

bitwrench does not need conditional rendering syntax. You are writing JS,
not a template language.

At define time: `c: [showChart ? makeChart(config) : null]`. The `if`
statement IS your conditional rendering.

At update time: handle method creates/destroys child components explicitly.
`bw.append()` to show. `bw.remove()` to hide. `bw.replace()` to swap.

React/Vue/Jinja need template-level conditionals (`{show && <Thing />}`,
`v-if`, `{% if %}`) because the developer's logic is separated from the
markup by a language boundary. In bitwrench, logic and UI are the same
language. CSS helpers like Less/Tailwind/CSS-vars melt away for the same
reason: when CSS is generated by JS functions with palette values, you
don't need a preprocessor.

### Reparenting (moving mounted components)

`newParent.appendChild(mountedEl)` -- the browser moves it. UUID, _nodeMap
entry, el.bw, state all survive. mounted() does NOT re-fire. No special
API needed. This is correct: the component was already mounted, it just
changed location.

### o.render functions are trusted code

`bw.refresh()` calls `el._bw_render(el, state)`. The render function
typically calls `bw.DOM(el, newTaco)` to replace children. bitwrench does
not validate or constrain what render functions do. This is the MFC/Qt
model (OnDraw can do anything), not React (render must be pure).

## Phase 6: Unmount

Element torn down. Hooks fired. Registrations cleared. State deleted.

| | |
|---|---|
| **Function** | `bw.cleanup(el)` |
| **Input** | Mounted element |
| **Output** | void |
| **Side effects** | Fires unmount hooks, deregisters from caches, unsubs pub/sub, deletes state |
| **In document** | Removed by caller (cleanup does NOT call el.remove()) |

### What cleanup does:

1. Find all `.bw_lc` elements in subtree (querySelectorAll)
2. For each (document order = root-to-leaf): get UUID, fire unmount
   callback, deregister from _nodeMap, call each unsub() in _bw_subs,
   delete _bw_state/_bw_render/_bw_refs/_bw_type/el.bw
3. Check the element itself (same steps)
4. Deregister non-lifecycle UUID elements from _nodeMap

### Cleanup order: root-to-leaf

querySelectorAll returns document order, which is root-to-leaf. This means
a parent's unmount hook fires BEFORE its children's unmount hooks. This is
correct: the parent can still read from child components during its own
teardown (`el.bw.getChartData()` etc). Children's unmount fires after,
then properties are deleted.

This is the opposite of SolidJS (leaf-to-root onCleanup) and the same
direction as MFC (DestroyWindow walks top-down).

### bw.cleanupChildren(el) (NEW)

Cleans up el's descendants but preserves el's own lifecycle. This replaces
the save/restore hack in current bw.DOM() (lines 1228-1246) with a clean
primitive.

bw.DOM() calls `bw.cleanupChildren(target)` instead of saving state,
calling cleanup, and restoring. No hack, no fragility.

## String Path (parallel, independent)

```
TACO --> bw.html(taco) --> HTML string
TACO --> bw.htmlPage(opts) --> complete HTML document
```

The string path does not go through create/hydrate/mount. It stamps
bw_uuid_* + bw_lc in markup if lifecycle hooks are present (forward
compat with future SSR hydration). No changes in v2.1.0.

## Framework Lifecycle Comparison

How other frameworks handle each phase. bitwrench does not copy these --
but we verify we have answers for the same problems, even if structurally
different.

### Phase-by-phase

#### Define

| Framework | Mechanism | Serializable? |
|---|---|---|
| **Vanilla JS** | No formal spec. HTML strings or imperative code. | N/A |
| **Bootstrap 5** | Static HTML + config object via `data-bs-*` or JS. | Config yes |
| **React** | JSX -> `React.createElement()` -> element descriptor. | Yes (minus fns) |
| **Vue 3** | SFC (.vue) or render function. | No (compiler) |
| **SolidJS** | JSX compiled to DOM creation code. Component fn runs once. | No (compiler) |

### Why pub/sub + method calls, not signals

SolidJS signals achieve the same end result as bitwrench handle methods --
a direct update to a specific DOM node, no VDOM diff. The difference is
automatic (signal subscription) vs explicit (pub/sub -> method call).

**Component "melting" vs persistence.** In SolidJS, the component function
runs once and dissolves into signal->DOM-node bindings. There is no
component entity after creation -- just a bag of reactive bindings. In
bitwrench, the component persists. `el.bw` exists from mount to unmount.

This matters for three reasons:

1. **Side effects are colocated.** `el.bw.setCount(5)` can validate,
   animate, update siblings, and mutate DOM -- all in one method. In
   Solid, the binding is in JSX, side effects in createEffect(), validation
   elsewhere. Three pieces that must be understood together but live apart.

2. **The component is the gate.** pub/sub calls the component's method.
   The component decides how to respond. Solid signals let anyone with a
   setter mutate state that directly touches DOM. No gate.

3. **Inspectability.** Once a Solid component melts, you can't find it via
   querySelector. solid-devtools reconstructs from internal ownership graph.
   bitwrench: `querySelector('.bw_is_component')` finds every live component.

**Where signals genuinely win:** Complex derived state with many deps.
`createMemo(() => a() + b())` auto-tracks. In bitwrench, you wire pub/sub
manually. More code, more chances for missed deps. For bitwrench's target
use cases (embedded, prototyping, server-driven), dep graphs are shallow
enough that explicit wiring is clearer.

**Performance is irrelevant at real-world scale.** The bottleneck is browser
layout/paint after DOM mutation, not JS dispatch. `el.textContent = 'x'`
costs microseconds; reflow costs milliseconds. Signal subscription vs
pub/sub handler vs direct method call: unmeasurable difference.

The frameworks with a REAL performance problem are those that diff VDOM
trees to figure out what changed (React, Vue default). They pay O(tree)
per state change. Frameworks with live component models (bitwrench, Solid,
MFC/Qt) go directly to the changed node. O(1).

For non-game apps, a few dozen updates per user action is typical. At that
scale ALL frameworks are fast. The "10K updates" benchmark is synthetic.
The real question is whether the update mental model is clear enough to
wire correctly on the first try -- that's a docs/examples problem.

### Alternative Update Paths

Someone will ask why not skip handle methods and write to DOM directly
via bw.el(). This section documents the tradeoffs.

**Path A: Method dispatch (recommended)**
```
bw.pub('data:update', newData)
--> subscriber calls bw.message(uuid, 'setValue', newData.count)
    --> el.bw.setValue(val) runs: validate, side effects, DOM mutation
```

**Path B: Direct DOM via bw.el() (escape hatch)**
```
bw.pub('data:update', newData)
--> mega-function:
    bw.el(uuid1).textContent = newData.count
    bw.el(uuid2).style.width = newData.pct + '%'
```
O(1) cached lookups. Functionally identical to Solid's signal->DOM binding.

**Path C: Page-as-component (the full bitwrench pattern)**
```
var dashboard = {
  t: 'div',
  c: [ header, statsRow, chartPanel, feed ],
  o: {
    state: { ... },
    handle: {
      updateStats: function(el, data) { el.bw.setRevenue(data.rev); ... },
      refreshChart: function(el, data) { ... }
    },
    slots: {
      revenue: '.stat-revenue',
      users:   '.stat-users',
      chart:   '.chart-area'
    }
  }
};
var el = bw.mount('#app', dashboard);
bw.sub('data:update', function(d) { el.bw.updateStats(d); }, el);
```
Entire page is one TACO. Slots for every updatable region. Handle methods
for every action. pub/sub wires data flow. O(1) slot updates, full pipeline
intact: encapsulation, inspectability, cleanup.

**Why Path A is recommended:**
1. Inspectability. Path B bypasses components -- they don't know they were
   updated. bw.inspect() shows stale state. Future bw.update() overwrites.
2. Correctness compounds. Add validation to a handle method, all callers
   get it for free.
3. Performance difference is zero. One extra function call = nanoseconds.

**When Path B is appropriate:** Custom visualization component that owns
many simple DOM nodes (sparkline rects, heatmap cells). The parent
component's handle method IS the mega-function.

**When Path C is appropriate:** Always. This is the canonical bitwrench
pattern at full scale. Paths A and B are for cases where the page isn't a
single component (independent widgets, third-party elements mixed in).

**Reflow reality:** Multiple DOM writes in one synchronous JS task cause
ONE reflow (browser batches). Path A (100 subscribers each writing one
node) and Path B (1 mega-function writing 100 nodes) cause the same
number of reflows: one. The exception is layout thrashing (reading
offsetHeight between writes forces intermediate reflow). That's a coding
mistake, not a framework issue. Document: "batch all writes, then read."

**The building blocks are there.** pub/sub, el/$, message, update, patch,
replace, append, remove, refresh, inspect -- all the primitives for any
update pattern. The API names tell you the cost. Developers who disagree
with our recommendation can build their preferred pattern.

#### Cloning / Reuse

| Framework | Mechanism | Identity |
|---|---|---|
| **Vanilla JS** | el.cloneNode(true) | No identity system |
| **Bootstrap 5** | Not supported. Must re-instantiate. | New instance per element |
| **React** | React.cloneElement() (clones descriptor) | key prop |
| **Vue 3** | Re-render component | Internal UID |
| **SolidJS** | Re-call component fn | New ownership scope |
| **Angular** | ViewContainerRef.createComponent() | New component ref |
| **MFC/Qt** | Create new object same params | New handle/pointer |
| **bitwrench** | Clone the TACO (plain data). Assign fresh UUID. | bw_uuid_* per instance |

**Rule: clone TACOs, not DOM nodes.** TACO is data. Clone it at define
time. `bw.assignUUID(clone)` for fresh identity. Functions in `o` are
shared by reference across clones (correct -- stateless, state is per-
instance on _bw_state). DOM cloneNode after hydrate produces a broken
element (classes present, JS properties missing, UUID collision on mount).

## Operations Across Contexts

The same operations are invoked from four different contexts. The API must
be clean and consistent across all of them.

### Context table

| Operation | Client JS | bwserve protocol | bwcli/bwattach | LLM intent |
|---|---|---|---|---|
| Call specific method | `bw.message(ref, 'setCount', 5)` | `{type:'message', ref, action, data}` | `bwcli message #stats setCount 5` | "set the count to 5" |
| Give new data | `bw.update(ref, data)` | `{type:'update', ref, data}` | `bwcli update #stats '{...}'` | "update stats with new data" |
| Modify attrs/text | `bw.patch(ref, content)` | `{type:'patch', ref, content}` | `bwcli patch #btn '{disabled:true}'` | "disable the button" |
| Replace element | `bw.replace(ref, taco)` | `{type:'replace', ref, taco}` | `bwcli replace #header '{t:"h1",...}'` | "swap the header" |
| Add child | `bw.append(ref, content)` | `{type:'append', ref, content}` | `bwcli append #list '{t:"li",...}'` | "add a list item" |
| Remove element | `bw.remove(ref)` | `{type:'remove', ref}` | `bwcli remove #banner` | "remove the error banner" |
| Force rebuild | `bw.refresh(ref)` | `{type:'refresh', ref}` | `bwcli refresh #dashboard` | "rebuild the dashboard" |
| Inspect | `bw.inspect(ref)` | `{type:'inspect', ref}` | `bwcli inspect` | "what components are on this page?" |
| Screenshot | `client.screenshot()` | `{type:'screenshot'}` | `bwcli screenshot` | "show me what it looks like" |

### Protocol-to-function mapping (bwserve)

Every bwserve protocol message type maps to exactly one client-side
function. No ambiguity, no overloading at the protocol level.

| Protocol type | Client function | Notes |
|---|---|---|
| `message` | `bw.message(ref, action, data)` | Component method dispatch |
| `update` | `bw.update(ref, data)` | Smart: method dispatch or refresh |
| `patch` | `bw.patch(ref, content)` | Attrs, text, or children |
| `replace` | `bw.replace(ref, taco)` | Swap element itself |
| `append` | `bw.append(ref, content)` | Add child |
| `remove` | `bw.remove(ref)` | Cleanup + remove |
| `refresh` | `bw.refresh(ref)` | Rebuild from render |
| `eval` | `eval(code)` | Escape hatch |
| `screenshot` | `client.screenshot()` | html2canvas capture |
| `navigate` | `location = url` | URL change |
| `inspect` | `bw.inspect(ref)` | Return component tree data |

### Server perspective

A server managing UI remotely thinks in terms of:
- "Show new data in this component" -> `update` (component decides how)
- "Replace that section with new content" -> `replace`
- "Change the button text" -> `patch`
- "Add a notification" -> `append`
- "Remove the error" -> `remove`
- "User switched views, rebuild" -> `refresh`
- "Call a specific action" -> `message`

Server-sent TACOs cannot contain functions, so `refresh` only works if
the component was created client-side with a render function. For purely
server-driven components, `replace` is the right operation.

### LLM/bwattach perspective

An LLM driving the UI via bwattach follows this loop:
1. `bw.inspect()` -- understand what components exist, their types, methods
2. Decide what to change
3. Call the appropriate operation (update, message, patch, replace, etc.)
4. `client.screenshot()` -- verify the result visually
5. Repeat

`bw.inspect()` returns el.bw method names, so the LLM knows what methods
each component supports. `bw.update(uuid, data)` is the "I don't know the
specific method, just give it data" shorthand. `bw.message(uuid, action, data)`
is the precise dispatch when the LLM knows the method name.

### Remote render (bwserve)

Server generates a TACO, sends it via SSE, client renders it. The full
pipeline:

```
Server: conn.send({type:'replace', ref:'#main', taco: {t:'div', c:[...]}})
Client: bw.replace('#main', taco)
  -> bw.cleanup(oldEl)
  -> node = bw.createDOM(taco)    // create+hydrate (no o.* in server TACO)
  -> parent.replaceChild(node, oldEl)
  -> _mountTree(node)             // stamps UUID, registers, fires mounted()
```

Server TACOs don't have `o.*` options (can't serialize functions), so
hydrate is a no-op. The mounted elements are structural -- addressable
by id or UUID for future patch/replace/remove, but no handle methods or
state. If the client needs lifecycle on server content, it creates the
component client-side and uses bwserve data to feed it.

### Remote debug (bwcli/bwattach)

bwcli connects to a running page and can:
- Inspect component tree (`bwcli inspect`)
- Call component methods (`bwcli message uuid action data`)
- Modify the live page (`bwcli patch`, `bwcli replace`, etc.)
- Capture screenshots (`bwcli screenshot`)
- Validate TACOs against schemas (`bwcli validate`)

All operations go through the same `bw.*` functions the client uses.
bwcli sends eval-wrapped function calls. The page's bitwrench instance
does the work. No special debug API -- the production API IS the debug API.

## Gaps and Open Questions

### GAP-1: _bw_refs when UUID moves to mount -- RESOLVED

createDOM auto-assigns UUID (class string) to elements with `o.*` lifecycle
options during create+hydrate. This is structural identity for _bw_refs
keying. The UUID is NOT registered in _nodeMap until mount. UUID class is
just a string in the class attribute -- assigning it during create doesn't
violate the phase model. Factories don't need to call `bw.assignUUID()`
manually; createDOM handles it.

### GAP-2: Standalone hydrate parallel walk

hydrate(node, taco) must pair node.childNodes with taco.c. They aren't
isomorphic (null -> text, raw -> fragment, text -> text node).

**Resolution**: hydrate walks taco.c, skipping non-TACO entries. For each
TACO with `o`, it matches to a child element by tag name + position among
same-tag siblings. This is imperfect but covers real use cases (server-
rendered HTML where structure matches the TACO). For the normal pipeline,
this doesn't matter -- createDOM fuses create+hydrate with exact pairing.

### GAP-3: bw.patch() doesn't clean up old children (BUG) -- FIX PLANNED

`bw.patch()` does `innerHTML = ''` then `appendChild(createDOM(content))`
when patching TACO/array content. No cleanup on old children. Unmount
hooks don't fire, _nodeMap leaks, pub/sub subs leak.

**Fix**: Call `bw.cleanupChildren(el)` before replacement. New content
goes through full pipeline: createDOM (create+hydrate) + _mountTree.
Same fix applies to `bw.replace()` which cleans up old element before
creating replacement.

### GAP-4: Slot setters need cleanup

Slot setters do `target.innerHTML = ''; target.appendChild(createDOM(value))`.
Same problem as GAP-3. Add cleanup before replacement.

### GAP-5: bw.DOM() save/restore hack

Current bw.DOM() saves target state, calls cleanup, restores. Fragile.

**Fix**: Replace with `bw.cleanupChildren(el)` (new function). Cleans up
descendants, preserves el's own lifecycle. bw.DOM() calls cleanupChildren
instead of the save/restore dance.

### GAP-6: bwserve "re-hydrate" (NOT v2.1.0)

Server sends structure, client wants to attach lifecycle. No clean path.
Future pattern. For now: server sends structure, client handles actions.
If client needs lifecycle, create the component client-side.

### GAP-7: State access is uncontrolled

el._bw_state is directly accessible. Handle methods are the intended gate
but not enforced.

**Options**:
- (a) Auto-create el.bw.getState()/setState(patch) during hydrate. setState
  could auto-trigger bw.refresh() + statechange emit.
- (b) Accept raw access. Document that _bw_state is internal.

Decide before implementation.

### GAP-8: Scale not verified

Need a benchmark page (500-1000 components). Expect it's fine. 1-hour task.

### GAP-9: Error handling in mount

If mount fails partway (e.g., UUID collision on child 50 of 100), the
first 49 are registered, rest are not.

**Resolution**: UUID collision = warn + skip (soft error). The colliding
element works structurally (in DOM) but has no lifecycle. Graceful
degradation. No rollback needed.

### GAP-10: Event listener tracking

addEventListener calls not tracked. Listeners leak on non-cleanup removal.

**Not for v2.1.0.** innerHTML = '' causes browser GC of listeners on
removed elements. Leak only happens with raw el.remove() without cleanup.
Revisit if measured as real issue.

## Design Decisions (locked for v2.1.0)

| Decision | Choice | Rationale |
|---|---|---|
| Handle API | el.bw (not Handle object) | Simpler, shipped, "DOM IS the registry" |
| Handle keyword | o.handle (not o.methods) | Shipped, documented, "methods" overloaded in JS |
| BCCL class rename | Separate release (not v2.1.0) | Too much mechanical churn alongside lifecycle refactor |
| Event listener tracking | Not v2.1.0 | Low priority, browser GC covers normal cases |
| TACO storage on element | No. TACO consumed during create+hydrate. | No real use case for clone-from-live or re-hydrate. If needed later, store proper deep clone, not partial. |
| mounted() timing | Synchronous (remove rAF) | Correct: element IS in document when hook runs |
| UUID collision | Warn + skip (soft error) | Hard throw leaves DOM in partial state |
| createDOM behavior | Returns hydrated-but-not-mounted node (create+hydrate fused) | Parallel walk for standalone hydrate is fragile; fusion is pragmatic |
| o.* option set | Final for v2.1.0. 7 options. No additions. | Complete, minimal, each has clear job |
| Auto-render-as-mounted | Keep. Documented behavior. | Eliminates boilerplate for common pattern |
| TACO JSON Schema | Ship base schema + validator in v2.1.0 | Structural validation without compiler. Works across languages, CI, LLMs. |
| bw.update() semantics | Smart dispatch: el.bw.update(data) if exists, else refresh | Name means what devs expect. Backwards compat: update(ref) with no data = refresh. |
| bw.refresh() | New. Explicit heavy rebuild from _bw_render. | Replaces ambiguous bw.update(). Name is honest about cost. |
| bw.replace() | New. Swap element at DOM position. Returns new element. | Clean API for "swap one component for another." Old ref is stale -- must return new. |

| bw.patch() scope | Keeps all overloads (attrs, text, TACO, array). Gets cleanup fix. | Splitting would be more churn than benefit. Overloading is well-understood. |
| Cleanup order | Root-to-leaf (document order) | Parent's unmount can still read children during teardown. |

## TACO JSON Schema (key deliverable for v2.1.0)

### Why

React's compile-time safety comes from JSX + TypeScript: the compiler
catches structural errors before runtime. But JSX is opaque to non-TS
tools -- you can't validate a JSX tree from a CI script, a JSON API, or
an LLM without running the compiler.

TACO is plain JSON (minus function values in `o`). A JSON Schema can
validate it with standard tools, no compiler needed. This gives bitwrench
something React cannot offer: **structural validation at define time that
works across languages, tools, and pipelines.**

### What this enables

1. **Editor autocomplete**: JSON Schema in VS Code gives property
   suggestions, type hints, and inline validation as you type TACOs.

2. **CI validation**: A GitHub Action runs `bwcli validate src/**/*.js`
   and catches malformed TACOs before merge. No compiler, no build step.

3. **LLM output validation**: An LLM generates a TACO (JSON). The schema
   validator checks it before hydration. Catches hallucinated tag names,
   invalid attribute types, impossible nesting. This is important for
   bwserve where server-sent TACOs drive the UI.

4. **Company-level compliance schemas**: A team extends the base schema
   with their own rules: "all buttons must have aria-label", "no inline
   styles", "only these BCCL components are approved". The validator
   enforces this automatically.

5. **bwserve protocol validation**: Server-sent TACO payloads validated
   against schema before client processes them. Catches protocol errors
   at the transport layer.

6. **BCCL component catalog schemas**: Each `bw.make*()` factory documents
   its expected config as a JSON Schema. `bw.catalog()` returns these.
   Tools can auto-generate forms for component configuration.

7. **Page/app-level schema validation**: A TACO for an entire page is one
   tree. A page-level schema can enforce "this dashboard must have a header,
   a stats row with 4 stat cards, and a chart panel." The validator checks
   the whole page structure in one pass. React can't do this -- a React page
   is scattered across dozens of component files with no single validatable
   artifact representing "the page." This is validation ABOVE the component
   level, not just at it.

8. **Shared schemas across teams and LLMs**: Teams publish their page/app
   schemas alongside their bwserve endpoints. An LLM generating UI for that
   app validates against the published schema. A backend team generating
   TACOs in Python validates against the same schema the frontend uses.
   bwserve infrastructure + shared schemas = a complete contract between
   server, client, LLM, and CI. No other framework has this as a standard
   capability.

### Schema hierarchy

Schemas compose from general to specific. Each level extends the one above.

```
taco.schema.json              -- base TACO format (bitwrench ships this)
  taco-bccl.schema.json       -- BCCL component schemas (bitwrench ships as example)
  taco-bwserve.schema.json    -- bwserve protocol messages (bitwrench ships this)
  company-components.schema.json -- team's own component library (team writes this)
    company-ui.schema.json    -- company branding/structure rules (team writes this)
      app-dashboard.schema.json  -- specific app page structure (team writes this)
```

Large teams will NOT use BCCL -- they build their own component library
with their own design system. Their component schemas extend taco.schema.json
directly, not taco-bccl.schema.json. BCCL schemas serve as a documented
example of how to write component schemas.

A company schema extends their component library: "all pages must have a
nav bar, only approved components, these palette colors." An app schema
extends the company schema: "dashboard has these 5 regions, stats row has
exactly 4 cards, chart panel accepts these data shapes." Validation runs
bottom-up -- a TACO that passes the app schema automatically passes all
parent schemas.

**Base TACO schema** (`taco.schema.json`):
- `t`: string (HTML tag name). Optional (text content if absent).
- `a`: object. Keys = attribute names. Values = string, number, boolean,
  or object (for style). `class` = string. `id` = string.
- `c`: string, number, null, TACO, or array of any of these. Recursive.
- `o`: object. Optional. Keys: `state`, `render`, `mounted`, `unmount`,
  `handle`, `slots`, `type`. Types: `state` = object, `render`/`mounted`/
  `unmount` = "function" (not validatable in JSON, documented as marker),
  `handle` = object of functions, `slots` = object of selector strings,
  `type` = string.

The schema validates STRUCTURE, not runtime behavior. Function values
in `o` are typed as `true` (presence marker) in the JSON schema since
JSON can't represent functions. The validator checks that `o.slots` values
are strings, `o.state` is an object, etc.

### Validator library

```javascript
bw.validateTaco(taco)
// Returns: { valid: true } or { valid: false, errors: [...] }
// errors: [{ path: 'c[2].a.class', message: 'expected string', got: 42 }]

bw.validateTaco(taco, schema)
// Custom schema (company rules, BCCL config schema, etc.)
```

Implementation: pure JS, no dependencies. ~200 lines. Validates against
the base schema by default. Custom schema parameter for extended rules.
Error messages include JSON path to the offending value.

Bundled into bitwrench core (tiny). Also available standalone for bwcli
and bwserve.

### bwcli integration

```bash
bwcli validate src/my-page.js          # validate TACO literals
bwcli validate --schema company.json   # custom schema
bwcli validate --strict                # all warnings become errors
```

bwcli's validate command extracts TACO-shaped object literals from JS
files (AST parse or regex heuristic) and runs them through the validator.
Functions in `o` are detected as present but not validated.

### bwserve integration

bwserve validates incoming protocol messages against `taco-bwserve.schema.json`
before processing. Invalid payloads are rejected with an error message
back to the server. This catches bugs in server-side TACO generation.

### How this compares to React's compile-time checking

| Concern | React + TypeScript | bitwrench + TACO Schema |
|---|---|---|
| **Structure validation** | JSX + TSX compiler | JSON Schema validator |
| **Works without build step** | NO (needs tsc) | YES (runtime or CI) |
| **Works across languages** | NO (TS only) | YES (any JSON Schema tool) |
| **Validates LLM output** | NO (LLMs don't emit TSX) | YES (LLMs emit JSON) |
| **Custom team rules** | ESLint plugins (complex) | Extend JSON Schema (standard) |
| **Props type checking** | TypeScript interfaces | BCCL component schemas |
| **State shape checking** | TypeScript (compile time) | Schema on o.state (define time) |
| **Runtime validation** | PropTypes (deprecated), Zod | bw.validateTaco() |
| **Server payload validation** | Manual (no standard) | taco-bwserve.schema.json |
| **Page-level validation** | NO (page = many files) | YES (page = one TACO tree) |
| **Cross-team schema sharing** | Not standardized | Publish schemas alongside bwserve endpoints |
| **LLM + server contract** | No standard | Shared schema: LLM, server, client, CI all validate same artifact |

**TypeScript parity via bitwrench.d.ts**: bitwrench already ships type
definitions. The `bw.make*()` factories are typed functions -- calling
`bw.makeTable({wrong: 'config'})` is a TS error today. This is the exact
equivalent of React's component prop interface checking: the factory
function signature IS the component contract. Hand-written TACOs get
structural typing from a `TACO` interface in the .d.ts. So for teams
using TypeScript, bitwrench has the same compile-time coverage as React.
The JSON Schema adds coverage for everyone NOT using TypeScript.

**Cross-component type inference**: React+TS tracks prop types across
component boundaries automatically. bitwrench gets this through factory
function signatures (TS) and through component catalog schemas (JSON
Schema). A lightweight bwcli tool could trace TACO composition across
files for non-TS projects -- the data format makes this straightforward
to build if someone needs it. React needed years of compiler infrastructure
for the same capability. bitwrench could add it in months because TACOs
are inspectable data, not opaque compiler artifacts.

Where TACO schema wins: validation that crosses language/tool boundaries.
A Python server generating TACOs for bwserve validates against the same
schema. A CI pipeline checks TACOs without running Node. An LLM's JSON
output is validated before touching the DOM. React has no answer for these
because JSX is a compiler artifact, not a data format.

**BCCL is a reference implementation, not a destination.** Large teams
will build their own component library on top of bitwrench core (lifecycle,
TACO, pub/sub, createDOM, bwserve). BCCL serves two roles: (1) a working
starter kit for prototyping and small projects, and (2) a documented example
of how to build components correctly using TACO + o.handle + o.slots. A
company's component library would define its own make*() factories with
their own schemas -- `company-button.schema.json` extending `taco.schema.json`,
not `taco-bccl.schema.json`. The schema hierarchy supports this naturally:
bitwrench ships the base TACO schema, BCCL ships component schemas as
examples, teams write their own component schemas for their own libraries.

**Page-level validation -- something React cannot do**: A React page is
composed of JSX spread across many files. There is no single artifact you
can hand to a validator and ask "does this page have the right structure?"
The closest equivalents are integration tests or Storybook stories, which
run the code. A TACO for a whole page IS one tree. Schema-validate it
statically. This is validation above the component level -- at the page,
app, and organizational level. React's tooling validates components in
isolation; TACO schemas validate the assembled result.

**The key insight**: TACO's advantage isn't "better than TypeScript" --
it's "validatable without TypeScript." And it's not just component-level
validation -- it scales UP to pages, apps, and cross-team contracts.
bitwrench doesn't need to conquer 1000-person teams. It needs to make
structural decisions that don't PRECLUDE them from building the right
tooling. TACO-as-data + JSON Schema + bwserve infrastructure is that
decision. React needed years of custom compiler work to build its
validation story. A bitwrench team could build equivalent coverage in
months because the data format is standard and the tools already exist.
