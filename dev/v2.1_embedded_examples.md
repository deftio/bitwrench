### v2.1 Wire Protocol Migration (prerequisite)

The C headers still emit v2.0 field names. The Python bwserve.py is already v2.1. This must be reconciled before any new examples ship.

| v2.0 field | v2.1 field | Affected files |
|------------|------------|----------------|
| `target` | `ref` | `bwserve.h`, `bitwrench.h` macros, all C examples |
| `node` | `taco` | `bwserve.h` replace/append macros, C++ wrappers |
| `content` | `text` | `bwserve.h` patch macros |
| (none) | `v: 1` | All protocol messages need version stamp |
| `replace` | `mount` | Message type name |
| `bw.loadDefaultStyles()` | `bw.loadStyles()` | `BW_BOOTSTRAP_HTML` in bwserve.h |

The Python `bwserve.py` already uses `ref`, `taco`, `text`, `mount`, `v: 1` — it's the reference implementation.

## Example 1: Sensor Dashboard (both boards)

**Goal:** "Unbox, flash, open browser" — zero or near-zero external parts.

### Variant A: Pico W — Built-in Sensors Only

**BOM:** Pico W ($6) + USB cable. Nothing else.

**What it shows:**
- On-die temperature sensor (ADC4) — live reading
- VSYS voltage — battery/USB voltage monitoring
- WiFi RSSI — signal strength
- Free memory — heap usage
- Uptime — running timer
- Onboard LED — toggle from browser

**Dashboard UI (served from the Pico):**
```
┌──────────────────────────────────────────────┐
│  Pico W Dashboard              [LED: ON/OFF] │
├──────────┬──────────┬──────────┬─────────────┤
│ Temp     │ Voltage  │ WiFi     │ Memory      │
│ 24.3°C   │ 4.92V    │ -42 dBm  │ 186 KB free │
├──────────┴──────────┴──────────┴─────────────┤
│ Uptime: 0h 14m 23s          Pico W / RP2040  │
└──────────────────────────────────────────────┘
```

**Components used:** `makeStatCard` (4 cards), `makeSwitch` (LED), `makeProgress` (memory bar), themed with `loadStyles()`.

**Update strategy:** SSE push every 2 seconds. `bw.patch()` for individual values — no full re-render.

**Implementations:**
1. **MicroPython** (`sensor_dashboard.py`) — recommended path, uses `embedded_python/bwserve.py`
2. **Arduino C++** (`sensor_dashboard.ino`) — uses `embedded_c/bwserve.h`

### Variant B: Pico W + I2C Accelerometer

**BOM:** Pico W ($6) + MPU6050 breakout ($2-3) + 4 jumper wires. The MPU6050 is the single most common I2C sensor in junk bins — it ships in every Arduino starter kit.

**What it adds on top of Variant A:**
- 3-axis acceleration (X, Y, Z) with live bar chart
- Gyroscope data (optional display)
- Tilt detection (binary indicator)
- Sample rate selector (100ms / 500ms / 1s)

**Wiring (I2C, 4 wires):**
```
Pico W          MPU6050
GP4 (SDA) ───── SDA
GP5 (SCL) ───── SCL
3V3       ───── VCC
GND       ───── GND
```

**Dashboard adds a chart section:**
```
┌──────────────────────────────────────────────┐
│  Accelerometer          [Rate: 500ms ▼]      │
├──────────────────────────────────────────────┤
│  X: ████████░░░░░░░░  0.42g                  │
│  Y: ██░░░░░░░░░░░░░░  0.08g                  │
│  Z: ██████████████░░  0.91g                  │
│                                    Tilt: No   │
└──────────────────────────────────────────────┘
```

**Components used:** `makeProgress` (3 bars), `makeSelect` (sample rate), `makeBadge` (tilt indicator).

### Variant C: XIAO ESP32-S3 — Built-in Sensors

**BOM:** XIAO ESP32-S3 ($5) + USB-C cable. Nothing else.

**What it shows:**
- On-chip temperature sensor
- WiFi RSSI
- Free heap + PSRAM usage
- Uptime
- Onboard LED (user-controllable)
- Battery voltage (if on battery)

Same dashboard structure as Variant A, but emphasizes the tiny form factor. Photo of the board next to a coin with the browser UI in the background.

## Example 2: Camera Viewer (XIAO ESP32-S3 Sense only)

**Goal:** The "wow" demo. A $14 board serves a camera UI with interactive controls. No app. No cloud.

**BOM:** XIAO ESP32-S3 Sense ($14) + USB-C cable. Camera and mic are soldered on.

### What it shows

The board captures JPEG frames from the OV2640 camera and pushes them to the browser. The browser renders a full control panel using bitwrench components. Controls talk back to the board via `bw_act_*` actions.

**Dashboard UI:**
```
┌──────────────────────────────────────────────┐
│  XIAO Camera                    [Save Photo] │
├──────────────────────────────────────────────┤
│                                              │
│           ┌──────────────────┐               │
│           │                  │               │
│           │   Camera Feed    │               │
│           │   (JPEG frame)   │               │
│           │                  │               │
│           └──────────────────┘               │
│                                              │
├──────────────────────────────────────────────┤
│ Resolution: [QVGA ▼]   FPS: 10              │
│ Brightness: [━━━━━━●━━━━]  Auto-Exp: [ON]   │
│ Quality:    [━━━●━━━━━━━]  Mirror:   [OFF]  │
├──────────────────────────────────────────────┤
│ Frame: 12.4 KB  │  WiFi: -38 dBm  │ 24.1°C │
└──────────────────────────────────────────────┘
```

### How it works

1. Board captures JPEG frame → base64-encodes → sends as `patch` to an `<img>` element's `src` attribute
2. Controls rendered as bitwrench components: `makeSelect` (resolution), `makeSwitch` (auto-exposure, mirror), slider for brightness/quality
3. User changes a control → `bw_act_*` CSS class fires a POST to the board → board changes OV2640 register → confirms via patch
4. "Save Photo" → board captures full-resolution frame → browser downloads via `bw.saveClientFile()`

### The "browser as coprocessor" moment

The climax insight: the ESP32 captures pixels, but the **browser** does the heavy lifting:
- Renders the full themed UI
- Decodes and displays the JPEG
- Handles the download/save
- Could do client-side image processing (crop, filter) and send results back

The microcontroller borrows the browser as a coprocessor. Name this explicitly in the tutorial.

### Frame delivery strategy

- JPEG at QVGA (320x240) ≈ 8-15 KB per frame
- Base64 overhead ≈ 33% → ~11-20 KB per SSE message
- At 5-10 FPS, that's 55-200 KB/s over WiFi — well within ESP32-S3 capability
- Alternative: serve frames via a separate `/stream` endpoint as MJPEG, reference in an `<img>` tag, use SSE only for controls and status. This is simpler and more efficient for the video stream while bitwrench handles the control panel.

### Implementation

- **Arduino C++** primary (ESP-IDF camera driver via `esp_camera.h`)
- **CircuitPython** possible but limited — CircuitPython camera support is experimental on the XIAO S3

### Flash budget

| Item | Size |
|------|------|
| Firmware (with camera driver) | ~800 KB |
| bitwrench.umd.min.js.gz | ~47 KB |
| Dashboard HTML | ~5 KB |
| **Total** | **~852 KB (10.6% of 8MB)** |

## Protocol Update Detail for C Headers

### Current (v2.0) → Target (v2.1)

**bwserve.h macros:**

```c
// BEFORE (v2.0):
#define BW_REPLACE(buf, target, taco_str) \
    snprintf(buf, sizeof(buf), \
        "r{'type':'replace','target':'%s','node':%s}", target, taco_str)

// AFTER (v2.1):
#define BW_MOUNT(buf, ref, taco_str) \
    snprintf(buf, sizeof(buf), \
        "r{'v':1,'type':'mount','ref':'%s','taco':%s}", ref, taco_str)
```

```c
// BEFORE:
#define BW_PATCH(buf, target, content) \
    snprintf(buf, sizeof(buf), \
        "r{'type':'patch','target':'%s','content':'%s'}", target, content)

// AFTER:
#define BW_PATCH(buf, ref, text) \
    snprintf(buf, sizeof(buf), \
        "r{'v':1,'type':'patch','ref':'%s','text':'%s'}", ref, text)
```

**Naming changes in macros:**
| v2.0 macro | v2.1 macro | Notes |
|------------|------------|-------|
| `BW_REPLACE` | `BW_MOUNT` | Type changed `replace` → `mount` |
| `BW_PATCH` | `BW_PATCH` | Same name, field names change |
| `BW_APPEND` | `BW_APPEND` | Field `node` → `taco` |
| `BW_REMOVE` | `BW_REMOVE` | Field `target` → `ref` |

**C++ namespace:**
| v2.0 | v2.1 |
|------|------|
| `bwserve::replace(target, taco)` | `bwserve::mount(ref, taco)` |
| `bwserve::patch(target, content)` | `bwserve::patch(ref, text)` |

**Backward compatibility:** Keep old macro names as `#define BW_REPLACE BW_MOUNT` aliases for one release cycle, with a comment marking them deprecated.

**Bootstrap HTML:** `bw.loadDefaultStyles()` → `bw.loadStyles()`.

## Open Questions

1. **MJPEG vs base64-over-SSE for camera:** MJPEG stream is more efficient and standard for video, but means the video stream bypasses bitwrench. Hybrid approach (MJPEG for video, SSE+bitwrench for controls) is probably right. Discuss.

2. **Lean vs full bundle for embedded:** Should embedded examples default to `bitwrench-lean.umd.min.js.gz` (37KB, no BCCL)? The sensor dashboard uses `makeStatCard`, `makeSwitch`, `makeProgress` — those are BCCL. So full bundle is needed if we use pre-built components. Alternative: hand-build the dashboard from raw TACOs (no BCCL) to show the 37KB lean path too.

3. **MicroPython SSE concurrency:** MicroPython on Pico W is single-threaded. The current `bwserve.py` `_serve_micropython()` uses blocking sockets. For the sensor dashboard to push SSE updates AND handle incoming actions, we likely need `asyncio` (available in MicroPython 1.19+) or microdot (already used in the Pico W tutorial's `server.py`). The existing Pico W server.py uses microdot — follow that pattern.

4. **Rust bindings:** `embedded_rust/` has a skeleton. Worth pursuing for the embedded launch, or save for later? Rust-on-embedded is a growing niche but smaller than C/Arduino + Python.

5. **Package manager registration:** The launch notes (D4) mention registering in Arduino Library Manager, PlatformIO registry, ESP-IDF component registry. This makes `embedded_c/` installable via `pio lib install bitwrench`. Worth doing before or after the article?
