### 2. Clean up `docs/thinking-in-bitwrench.md` remaining forward references

**Severity**: Medium/High for newcomer docs. The first half is now good, but the back half still needs a precision pass.

What improved:

- The doc now has the right teaching spine: TACO -> `bw.html()` -> nested TACOs -> `bw.mount()` -> `bw.create()` -> `bw.DOM()` / `bw.el()` -> composition -> styling -> events -> lifecycle.
- `o:` is introduced lightly in the TACO shape table, then deferred until the lifecycle section. That is the right kind of forward reference.
- Styling now grows from normal `class` / `style` to `bw.s()`, `bw.css()`, and theme helpers instead of starting as an API dump.

Remaining issues:

- [ ] `bw.refresh()` is mentioned in the Path L explanation before lifecycle/state explains what it does.
- [ ] `bw.$()` appears in the form example before it is introduced.
- [ ] `bw.apply()` appears in the bwserve diagram before protocol application is explained.
- [ ] The update cost spectrum lists `bw.message()`, `bw.update()`, `bw.patch()`, `bw.replace()`, and `bw.refresh()` together before all of those are introduced.
- [ ] The pub/sub example assumes a `navEl` component already exists, which is a small jump for a first-time reader.
- [ ] The bwserve section uses `client.render('#app', ...)`; if v2.1's preferred public name is `client.mount(...)`, this doc should teach `client.mount(...)`.
- [ ] The bwserve batch example still uses old wire-ish fields: `{ type: 'patch', target: '#status', content: 'Done.' }`.
- [ ] The bwserve diagram uses shorthand like `{replace, #app, taco}` and `{patch, #counter, "42"}`. That is readable, but v2.1 changed protocol names enough that the doc should either use precise `ref` / `taco` / `text` language or stay intentionally non-JSON.
- [ ] The BCCL section says all BCCL factories wire up `o.handle` and/or `o.slots`. Verify that this is literally true, or soften it to "many BCCL components".
- [ ] The `bw.derive()` example should be checked against the implemented v2.1 signature. The current example may be an old positional form.

Reasoning:

The early rewrite solved the large problem. A reader can now learn the core model without first memorizing lifecycle, raw HTML, server rendering, and BCCL. The remaining problem is that later sections start behaving like a reference again and introduce helper names faster than the doc has prepared the reader.

For a first-time document, small unexplained helper names matter. If the user is still learning the idea that "a TACO is just data", seeing `bw.$()`, `bw.apply()`, `bw.message()`, and `bw.update()` too early makes them read around unknown names instead of following the model.

Done when:

- [ ] No `bw.*` helper appears in a teaching example before either being introduced or explicitly labeled "covered later".
- [ ] `bw.refresh()` first appears where `o.state` / `o.render` are explained, or earlier mentions say only "covered later".
- [ ] The form example either explains `bw.$()` first or uses `document.querySelector()`.
- [ ] The first bwserve diagram does not require understanding `bw.apply()`.
- [ ] The bwserve section uses v2.1 names and message shapes.
- [ ] The update spectrum is framed as a later map, not as concepts the reader must already know.
- [ ] `bw.derive()` example matches the implementation.

### 4. Migrate bwserve documentation to v2.1

**Severity**: High.

Primary files:

- [ ] `docs/bwserve.md`
- [ ] `docs/tutorial-bwserve.md`
- [ ] `docs/app-patterns.md`
- [ ] `docs/llm-bitwrench-guide.md`
- [ ] `docs/bitwrench-for-wasm.md`
- [ ] `docs/cli.md`

Observed drift:

- `docs/bwserve.md` still says there are "9 protocol message types covering DOM operations and remote execution".
- It still shows `{type,node}` and `client.render()`.
- It still lists `exec` as a protocol operation.
- It still describes `data-bw-action` as backwards compatible.
- It still shows wire messages with `target`, `node`, and `content`.
- `docs/tutorial-bwserve.md`, `docs/app-patterns.md`, and `docs/llm-bitwrench-guide.md` still use `client.render(...)`.
- `docs/llm-bitwrench-guide.md` still lists `exec` in the protocol summary.
- `docs/cli.md` still shows old `target` / `content` patch messages and `/exec`.
- `docs/bitwrench-for-wasm.md` still describes `exec` and old `target` / `node` messages.

Reasoning:

Docs are executable training material for users and LLMs. If official docs still teach `target` / `node` / `content` and `exec`, those names will continue to show up in generated examples, issue reports, and demos.

This is especially important for bitwrench because one of v2.1's strongest claims is "code never crosses the wire." Any doc that presents `exec` as normal weakens that claim.

Done when:

- [ ] bwserve docs teach only the v2.1 protocol: `v:1`, `ref`, `taco`, discriminated patch fields, `bw_act_*`, `bw.remote`, `listen`, and `unlisten`.
- [ ] `client.mount(...)` is the primary public example if that is the intended v2.1 name.
- [ ] `client.render(...)` is removed from examples or explicitly marked deprecated compatibility.
- [ ] `exec` is removed from normal protocol docs, or isolated in a clearly unsafe debug/legacy document.
- [ ] `data-bw-action` is removed from v2.1 examples, or isolated as historical compatibility.
- [ ] WASM/embedded docs explain whether examples are using bwserve protocol or a custom micro-protocol.

### 6. Fix TypeScript definitions

**Severity**: High.

Primary files:

- [ ] `src/bitwrench.d.ts`
- [ ] `dist/bitwrench.d.ts`

Current improvements:

- `createDOM` and `cleanup` no longer appear in the scanned `src/bitwrench.d.ts` surface.
- `bw.on(...)` is now typed as returning `() => void`.
- `bw.update(ref, data)` is now described as dispatch, not render.

Remaining issues:

- [ ] `DOM(...)` comment still says "Returns the target element"; v2.1 says `bw.DOM` is an exact alias of `bw.mount()` and returns the inserted root.
- [ ] Generated `create*` component functions still appear in the type surface even though the v2.1 suite asserts the generated `create*` family is gone at runtime.
- [ ] `apply(msg: Record<string, any>)` is too loose for a release where wire schema correctness is central.
- [ ] `patch(...)` type still exposes the old positional `content, attr` shape, while v2.1 wire patches use discriminated fields. Runtime may still support local positional patching, but types should make the distinction clear.
- [ ] CSS/theme methods should be checked against v2.1 return contracts, especially `setThemeMode`, `toggleThemeMode`, `applyStyles`, and `loadStyles`.

Reasoning:

Types are executable documentation for editors, users, and agents. If the runtime removed generated `create*` APIs but the `.d.ts` file still advertises them, TypeScript users will write code that fails at runtime.

Done when:

- [ ] `bw.DOM` and `bw.mount` comments and return types match the root-return contract.
- [ ] Removed runtime APIs are removed from both `src` and `dist` type definitions.
- [ ] Wire message types are represented as discriminated unions or equivalent documented interfaces.
- [ ] Local patch API and wire patch API are not blurred together.
- [ ] Types align with generated API docs.

### 7. Decide what to do with `src/bwserve/bwclient.js` compatibility paths

**Severity**: Medium/High.

Current improvements:

- Built-ins are now registered locally with `bw.registerRemote(...)`, not by sending function source through wire `register`.
- The previous obvious `new Function(...)` paths are no longer present in the scanned file.
- `bw.remote = { send(msg) }` is installed.

Remaining issues:

- [ ] File-level comments still say `data-bw-action click/key delegation`.
- [ ] `_wireActions()` still supports `data-bw-action`.
- [ ] `_wireActions()` is a separate delegated action path instead of clearly relying on the core `bw_act_*` dispatcher.
- [ ] `_bw_mount` still accepts an options object with `target`, which may be acceptable as an internal attach helper but should not look like public wire protocol.
- [ ] `_bw_listen` / `_bw_unlisten` still use selector/event listening, while the v2.1 protocol emphasizes topic `listen` / `unlisten`.

Reasoning:

This file is injected into real bwserve pages, so readers and tools will treat it as the actual browser client contract. If compatibility paths stay, they need to be explicitly walled as attach/debug/internal behavior and not presented as the normal bwserve protocol.

Done when:

- [ ] Normal bwserve action dispatch goes through `bw_act_*` and `bw.remote`.
- [ ] `data-bw-action` support is removed or explicitly marked legacy/debug-only.
- [ ] `_bw_mount`, `_bw_listen`, and `_bw_unlisten` are either migrated to v2.1 names/semantics or clearly documented as internal attach helpers.
- [ ] A browser/Playwright gate proves the injected shell can mount, patch, send `bw_act_*`, and forward topic listens without code-over-wire behavior.

### 10. Decide whether "levels" remains an advanced taxonomy

**Severity**: Medium.

Observed drift:

- `docs/thinking-in-bitwrench.md` no longer uses "levels" as the first teaching spine, which is good.
- Other docs/pages still use "Level 0 / Level 1 / Level 2" heavily:
  - [ ] `docs/state-management.md`
  - [ ] `docs/llm-bitwrench-guide.md`
  - [ ] `pages/05-state.html`
  - [ ] `pages/11-debugging.html`
  - [ ] selected examples/readmes

Reasoning:

The levels taxonomy is not inherently wrong. It can be useful after the reader understands TACO data, DOM mounting, state, and lifecycle. The problem is using it as the first explanatory frame. Newcomers do better with a serial model: "object becomes HTML, object becomes DOM, JavaScript composes objects, behavior/lifecycle/server come later."

Done when:

- [ ] Beginner pages avoid using levels as the primary teaching spine.
- [ ] Advanced/reference pages may keep levels, but define them only after the core model is established.
- [ ] Cross-links from beginner pages point to the serial docs first, not levels-heavy docs.

Reasoning:

Candidate denylist for public docs/pages/examples:

- `target` in bwserve protocol examples
- `node` in bwserve protocol examples
- `content` as old patch field
- `client.render`
- `data-bw-action`
- `exec`
- `register` as a wire verb
- `allowExec`

- `createDOM`

This should not be a blind global grep. Some words are legitimate in prose or unrelated code. The useful gate is an allowlisted drift scan over release-facing examples and generated docs.

Done when:

- [ ] There is a documented command or checklist for v2.1 release drift.
- [ ] Intentional legacy/historical hits are allowlisted with comments.

## Reviewer Bottom Line

The refactor itself looks much better than the surrounding ecosystem. The lifecycle and core v2.1 behavior are holding up. The remaining release problem is consistency: public surfaces still teach multiple generations of bitwrench at once.

For release readiness, the key question is:

> Can a newcomer, LLM, or official tool still learn or execute the old 2.0.x protocol from a release-facing surface?

If yes, it belongs on this checklist.
