# bitwrench embedded C/C++

C/C++ headers for building bwserve-compatible servers on embedded systems (ESP32, STM32, RP2040, etc).

## Files

| File | Description |
|------|-------------|
| `bitwrench.h` | TACO format helpers — macros for composing UI node JSON strings |
| `bwserve.h` | bwserve protocol — mount, patch, append, remove, batch, SSE frames; inbound actions; client registry |
| `bitwrench_embedded.h` | The minified bundle, gzipped, as a flash array — serve `/bitwrench.js` with no filesystem (generated) |
| `bitwrench_embedded_lean.h` | Same, lean build (no BCCL component factories) |

Everything is header-only, C99, no dependencies, and compiles as C or C++.

itself stays in flash and is streamed, never copied into RAM.

### Copy the headers (always works)

Both files are header-only with no dependencies — copying them is a
perfectly good install method.

**Arduino IDE** — copy both header files into your sketch folder:

```
my_project/
  my_project.ino
  bitwrench.h
  bwserve.h
```

**PlatformIO** — copy headers into a library folder:

```
lib/
  bitwrench/
    bitwrench.h
    bwserve.h
```

**CMake / esp-idf** — add the `embedded_c/` directory to your include path:

```cmake
target_include_directories(my_app PRIVATE path/to/embedded_c)
```

No linking required — both files are header-only.

## Serving bitwrench.js with no filesystem

The board has to answer `GET /bitwrench.js`. Mounting LittleFS or SPIFFS just
for that is a partition, a build step and a flashing step; `bitwrench_embedded.h`
is the alternative — the gzipped bundle as a `PROGMEM` array, served straight
from flash:

```cpp
#include <bitwrench_embedded.h>     // ~46 KB of flash

server.on("/bitwrench.js", HTTP_GET, []() {
    server.sendHeader("Content-Encoding", "gzip");
    server.sendHeader("Cache-Control", "max-age=31536000, immutable");
    server.send_P(200, "application/javascript",
                  (const char *)bitwrench_js_gz, bitwrench_js_gz_len);
});
```

The browser decompresses it; the device never does. Swap in
`bitwrench_embedded_lean.h` (~36 KB) if you do not use the `make*()` component
factories — see the Size table above.

Both headers are generated at release time from the bundle that ships, and each
carries `BITWRENCH_EMBEDDED_VERSION` plus the SRI hash of its source, so a
stale copy is obvious:

```c
Serial.println(BITWRENCH_EMBEDDED_VERSION);   // "2.1.11"
```

No filesystem, no CDN, no internet: the whole UI is served by the device, which
is the point on an isolated network.

## Handling clicks from the browser

Everything above pushes UI out. A button rendered with a `bw_act_*` class posts
back to the device, and `bw_parse_action()` reads it without pulling in a JSON
parser.

**Two clients, two URLs.** Which one you get depends on the page, and
`bw_parse_action()` accepts either body:

| Page uses | Posts to | Body |
|-----------|----------|------|
| `bw.actions.enable()` + `bw.connect('/bw/events')` -- the four-line page, and what the demos use | `POST /bw/events` (the same URL as the stream) | `{"v":1,"type":"event","action":"gpio-toggle","value":null,"name":null}` |
| the bwserve thin client (`bwclient.js`, served by the bwserve shell) | `POST /bw/return/action/<clientId>` | `{"result":{"action":"gpio-toggle","data":{"pin":17}}}` |

Note that `bw.actions` is **off until you call `bw.actions.enable()`** --
`bw.connect()` does not turn it on. A page that only connects gets a live
stream and dead clicks.

With the first shape the values are top-level (`value`, `name`); with the
second they sit inside `data`. `bw_action_field()` looks in both, so firmware
needs one code path:

```c
/* the button: class "bw_act_gpio-toggle", with data the client sends along */
char taco[BW_TACO_BUF_SIZE], msg[BW_BUF_SIZE];
BW_TACO_CLS(taco, "button", "bw_act_gpio-toggle bw_bccl_btn", "Toggle");
BW_MOUNT(msg, "#controls", taco);

/* ... and the POST handler */
bw_action_t act;
char pin[8];
if (bw_parse_action(request_body, &act)) {
    if (strcmp(act.action, "gpio-toggle") == 0 &&
        bw_action_field(&act, "pin", pin, sizeof pin)) {
        digitalWrite(atoi(pin), !digitalRead(atoi(pin)));
    }
}
```

`bw_parse_action()` accepts both strict JSON and the relaxed single-quoted form,
copies the action name into a fixed buffer, and points `act.data` into your
request body without allocating. `bw_action_field()` pulls one string or number
out of that data.

## More than one browser

A phone and a laptop watching the same board is normal. `bw_clients_t` is a
fixed-size registry of whatever handle your HTTP stack uses:

```c
static bw_clients_t clients;        /* BW_MAX_CLIENTS, default 4 */

void setup(void) { bw_clients_init(&clients); }

/* when an SSE connection opens / closes */
bw_clients_add(&clients, client_fd);
bw_clients_remove(&clients, client_fd);

/* push to everyone; a send that returns 0 drops that client */
static int write_sse(int fd, const char *frame, void *user) {
    (void)user;
    return send(fd, frame, strlen(frame), 0) > 0;
}

char frame[BW_BUF_SIZE];
BW_PATCH(msg, "temp", "21.5C");
BW_SSE_FRAME(frame, msg);
bw_clients_each(&clients, write_sse, frame, NULL);
```

Raise the ceiling with `-DBW_MAX_CLIENTS=8` if you expect more. The cost is
`BW_MAX_CLIENTS * sizeof(int)` of RAM and nothing else.

### The shape on a board

Only the transport differs. The four routes, with ESPAsyncWebServer:

```cpp
#include "bitwrench.h"
#include "bwserve.h"
#include "bitwrench_embedded.h"      /* the gzipped bundle, in flash */

AsyncWebServer server(80);
AsyncEventSource events("/bw/events");

/* 1. the bundle, straight out of flash -- no filesystem, no CDN */
server.on("/bitwrench.js", HTTP_GET, [](AsyncWebServerRequest *req) {
    auto *r = req->beginResponse_P(200, "application/javascript",
                                   bitwrench_js_gz, bitwrench_js_gz_len);
    r->addHeader("Content-Encoding", "gzip");
    r->addHeader("Cache-Control", "max-age=31536000, immutable");
    req->send(r);
});

/* 2. a page that owns no UI: load, style, enable actions, connect */
static const char PAGE[] =
    "<!DOCTYPE html><html><head><meta charset=\"utf-8\">"
    "<script src=\"/bitwrench.js\"></script></head>"
    "<body><div id=\"app\"></div><script>"
    "bw.loadStyles({ primary: '#0b7285', mode: 'auto' });"
    "bw.actions.enable();"              /* required -- bw.connect does not do it */
    "bw.connect('/bw/events');"
    "</script></body></html>";

server.on("/", HTTP_GET, [](AsyncWebServerRequest *req) {
    req->send(200, "text/html", PAGE);
});

/* 3. on connect, mount the whole UI; later, patch what changed */
events.onConnect([](AsyncEventSourceClient *client) {
    char label[BW_TACO_BUF_SIZE], value[BW_TACO_BUF_SIZE], btn[BW_TACO_BUF_SIZE];
    char kids[BW_BUF_SIZE];
    char card[BW_BUF_SIZE * 2];      /* each level larger than the last */
    char msg[BW_BUF_SIZE * 4];

    BW_TACO_CLS(label, "div", "bw_text_muted", "Count");
    BW_TACO_ID(value, "div", "count", "0");

    /* The control. `bw_act_increment` is the whole event wiring: it is what
       makes the POST handler below reachable, so it has to be in the tree. */
    BW_TACO_ATTR(btn, "button",
        "'class':'bw_bccl_btn bw_bccl_btn_primary bw_act_increment'", "+1");

    BW_ARRAY_START(kids);
    BW_ARRAY_ITEM(kids, label);
    BW_ARRAY_ITEM(kids, value);
    BW_ARRAY_ITEM(kids, btn);
    BW_ARRAY_END(kids);

    /* BW_NEST*, not a hand-built string: it strips the children's r-prefix,
       which a nested TACO must not keep or the frame will not parse. */
    BW_NEST_CLS(card, "div", "bw_bccl_card bw_p_3", kids);
    BW_MOUNT(msg, "#app", card);
    client->send(msg);
});

/* 4. a bw_act_* click posts to the SSE url itself (see "Handling clicks") */
server.on("/bw/events", HTTP_POST, [](AsyncWebServerRequest *req) {},
    NULL,
    [](AsyncWebServerRequest *req, uint8_t *data, size_t len, size_t, size_t) {
        /* Copy into a NUL-terminated buffer of our own. Writing data[len] = 0
           would run one past the framework's buffer. */
        char body[BW_BUF_SIZE], msg[BW_BUF_SIZE];
        size_t n = len < sizeof body - 1 ? len : sizeof body - 1;
        memcpy(body, data, n);
        body[n] = '\0';

        bw_action_t act;
        if (bw_parse_action(body, &act) &&
            strcmp(act.action, "increment") == 0) {
            static int count = 0;
            char txt[12];
            snprintf(txt, sizeof txt, "%d", ++count);
            BW_PATCH(msg, "count", txt);     /* name what changed */
            events.send(msg, NULL, millis());
        }
        req->send(204);
    });

server.addHandler(&events);
server.begin();
```

The button that drives route 4 is the `bw_act_increment` item in that array.
A class is the whole event wiring -- no `onclick`, and no handler crosses the
wire in either direction.

> The desktop demos above are compiled and executed by
> `test/bitwrench_test_embedded_c.js` on every run. **This ESP32 snippet is the
> same logic with ESPAsyncWebServer calls substituted and is not built in CI**,
> because the Arduino toolchain is not part of the test matrix. A per-stack
> adapter (`bw_attach(server)`) that removes this boilerplate is planned -- see
> [`dev/bw-embedded-release-plan-2.1.x.md`](../dev/bw-embedded-release-plan-2.1.x.md).

For a complete hardware sketch that takes the other approach -- the device

## Relaxed JSON (r-prefix)

All macros produce r-prefixed relaxed JSON so you avoid escaping double quotes:

```c
// Without r-prefix (painful):
const char* msg = "{\"v\":1,\"type\":\"patch\",\"ref\":\"temp\",\"text\":\"23.5\"}";

// With r-prefix (readable):
BW_PATCH(buf, "temp", "23.5");
// -> r{'v':1,'type':'patch','ref':'temp','text':'23.5'}
```

The browser's `bw.parseJSONFlex()` normalizes to strict JSON before processing.
r-prefix is outbound only (device to browser). The browser always sends strict JSON back.

## Batch Updates

Send multiple updates atomically:

```c
bw_batch_t batch;
bw_batch_begin(&batch);

char m1[256], m2[256];
BW_PATCH(m1, "temp", "23.5 C");
BW_PATCH(m2, "humidity", "67%");
bw_batch_add(&batch, m1);
bw_batch_add(&batch, m2);

char out[2048];
bw_batch_end(out, sizeof(out), &batch);
```

## C++ API

When compiled as C++, you get a cleaner namespace-based API:

```cpp
#include "bwserve.h"

auto node = bw::taco("h1", "Hello");
auto msg  = bwserve::mount("#app", node);
auto frame = bwserve::sse_frame(msg);

auto update = bwserve::batch({
    bwserve::patch("temp", "23.5"),
    bwserve::patch("humidity", "67%")
});
```

`std::string` means no fixed buffers and no truncation, so this is where
composing a whole screen is comfortable:

| Function | Purpose |
|----------|---------|
| `bw::taco(tag, text)` | Leaf node |
| `bw::taco(tag, cls, text)` | Leaf with a class |
| `bw::taco_id(tag, id, text)` | Leaf with an id (the patch handle) |
| `bw::taco_attr(tag, attrs, text)` | Leaf with a pre-composed attribute string |
| `bw::taco_num(tag, value)` | Leaf with a numeric value |
| `bw::nest(tag, children)` | Node whose content is other nodes |
| `bw::nest(tag, cls, children)` | ...with a class |
| `bw::nest_attr(tag, attrs, children)` | ...with arbitrary attributes |
| `bw::array({a, b})` / `bw::array(vec)` | A child list, fixed or data-driven |
| `bw::escape(str)` | Escape dynamic text before it goes in a value |

Protocol side:

| Function | Purpose |
|----------|---------|
| `bwserve::mount(ref, taco)` | Replace a target's children with this tree |
| `bwserve::append(ref, taco)` | Add a child |
| `bwserve::remove(ref)` | Remove the target |
| `bwserve::patch(ref, text)` | New text content |
| `bwserve::patch_num(ref, value)` | New numeric content |
| `bwserve::patch_attr(ref, text, attrs)` | Text **and** attributes in one op |
| `bwserve::message(level, text)` | A notification; arrives on `bw:message` |
| `bwserve::batch({...})` / `batch(vec)` | Several ops, one frame |
| `bwserve::sse_frame(msg)` | Wrap as `data: ...\n\n` |

These build with `std::string`, so there is no size cap and no buffer to pass.
(The C macros take a caller-supplied buffer instead, which is the right
behaviour for firmware with no heap. Before 2.1.11 the C++ wrappers copied
through a 512-byte buffer and truncated a page-sized `mount` in silence.)

`message()` is published on the `bw:message` topic rather than rendered --
where a notification belongs is the page's decision:

```javascript
bw.sub('bw:message', function(m) { bw.patch('status', m.text); });
```

Both `array()` and `nest()` take and return ordinary TACO strings, so a UI is
just functions that return strings:

```cpp
std::vector<std::string> rows;
for (int i = 0; i < n_sensors; i++)
    rows.push_back(bw::taco("li", sensor_name[i]));

std::string page = bw::nest("div", "bw_bccl_card", bw::array({
    bw::taco("h2", "Sensors"),
    bw::nest("ul", bw::array(rows))
}));
send(bwserve::sse_frame(bwserve::mount("#app", page)));
```

A full program built this way is in
[`examples/embedded/posix-cpp/`](../examples/embedded/posix-cpp/).

## Reference

### TACO Macros (bitwrench.h)

| Macro | Output |
|-------|--------|
| `BW_TACO(buf, tag, text)` | `r{'t':'tag','c':'text'}` |
| `BW_TACO_CLS(buf, tag, cls, text)` | `r{'t':'tag','a':{'class':'cls'},'c':'text'}` |
| `BW_TACO_ID(buf, tag, id, text)` | `r{'t':'tag','a':{'id':'id'},'c':'text'}` |
| `BW_TACO_ATTR(buf, tag, attrs, text)` | `r{'t':'tag','a':{attrs},'c':'text'}` |
| `BW_TACO_NUM(buf, tag, value)` | `r{'t':'tag','c':'23.5'}` |
| `BW_NEST(buf, tag, children)` | `r{'t':'tag','c':children}` -- content is TACOs, not text |
| `BW_NEST_CLS(buf, tag, cls, children)` | `r{'t':'tag','a':{'class':'cls'},'c':children}` |
| `BW_NEST_ATTR(buf, tag, attrs, children)` | `r{'t':'tag','a':{attrs},'c':children}` |
| `BW_ARRAY_START/ITEM/END(buf, ...)` | `[{...},{...}]` -- a child list |
| `BW_SKIP_R(taco)` | Drops the r-prefix of a TACO being nested (the macros above do this for you) |

The `BW_TACO_*` macros quote their content, which makes them leaves. Use
`BW_NEST*` for anything that holds other nodes, so a whole screen goes out in
one message:

```c
char label[256], value[256];
char kids[512];
char card[1024];      /* larger than kids */
char msg[2048];       /* larger than card */
BW_TACO_CLS(label, "div", "bw_text_muted", "Temperature");
BW_TACO_ID(value, "div", "temp", "22.4 C");
BW_ARRAY_START(kids);
BW_ARRAY_ITEM(kids, label);
BW_ARRAY_ITEM(kids, value);
BW_ARRAY_END(kids);
BW_NEST_CLS(card, "div", "bw_bccl_card bw_p_3", kids);
BW_MOUNT(msg, "#app", card);
```

Each level needs its own buffer: building a node into the buffer it is reading
from is undefined behaviour. The C++ helpers below have no such trap and no
size cap.

### Protocol Macros (bwserve.h)

| Macro | Description |
|-------|-------------|
| `BW_MOUNT(buf, ref, taco)` | Mount TACO node into target element |
| `BW_PATCH(buf, ref, text)` | Update target's text content |
| `BW_PATCH_NUM(buf, ref, value)` | Patch with a numeric value |
| `BW_PATCH_ATTR(buf, ref, text, attrs)` | Patch text + attributes |
| `BW_APPEND(buf, ref, taco)` | Append child to target |
| `BW_REMOVE(buf, ref)` | Remove target from DOM |
| `BW_BATCH(buf, ops)` | Wrap ops in a batch |
| `BW_MESSAGE(buf, level, text)` | Send a notification |
| `BW_SSE_FRAME(buf, data)` | Wrap as SSE `data:` frame |
| `BW_SSE_HEADERS` | HTTP headers for SSE response |
| `BW_BOOTSTRAP_HTML` | Legacy filesystem page: script tag + stylesheet link + `bw.loadStyles()`. Does **not** connect to SSE or enable actions |
